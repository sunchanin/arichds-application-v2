## Job A วัดจริงก่อนอ้าง — ตามกฎที่เพิ่งเพิ่ม

หลังบทเรียนของ #18 (คอมเมนต์อ้างเรื่อง index ที่ไม่จริง) prompt ของใบนี้ถูกสั่งว่า *"ถ้าจะอ้างเรื่องต้นทุนหรือ query plan ให้วัด ไม่งั้นอย่าอ้าง"* · Job A วัดสี่อย่างบนเครื่องนี้จริงก่อนเขียน prompt:

1. **`DELETE … LIMIT` เป็น syntax error** — SQLite ที่มากับ CPython ไม่ได้ build ด้วย `SQLITE_ENABLE_UPDATE_DELETE_LIMIT` (`REMAKE-PLAN.md:280` บันทึกไว้แล้วว่าเป็นเหตุให้ retention ของ v1 ต้องเขียนใหม่เป็น subquery) · รูปที่ใช้ได้คือ `DELETE FROM t WHERE id IN (SELECT id FROM t WHERE col < :cutoff LIMIT :n)`
2. **`VACUUM INTO` ปฏิเสธไฟล์ที่มีอยู่แล้ว** → ต้อง unlink temp **ก่อน**ใช้ ไม่ใช่แค่หลังพลาด
3. **`VACUUM INTO` ทำงานผ่าน SQLAlchemy ได้ทั้งสามโหมด** — pysqlite ไม่ส่ง `BEGIN` ก่อนคำสั่งที่ไม่ใช่ DML ข้อจำกัด "VACUUM รันใน transaction ไม่ได้" จึงไม่กัด · ไม่ต้องเต้น autocommit แก้ปัญหาที่ไม่มีอยู่
4. **batch delete ไม่ต้องใช้ index ใหม่** — วัดที่เคสแย่สุดที่ `REMAKE-PLAN.md:272` บันทึก (20 มิเตอร์ Modbus ล้วน → 28,800 แถว/วัน → ที่ retention 90 วันคือ 2.62 ล้านแถว 375 MB): ลบหนึ่งวันใช้ **7 batch / 1.61 วินาที** ที่ batch size 5000

ตัวเลข 5000 จึงเข้าไปอยู่ใน `constants.py` **พร้อมเงื่อนไขที่วัด** ไม่ใช่ตัวเลขลอย ๆ

ที่แย่คือ docstring ของคลาสเทสเขียนคุณสมบัตินี้ไว้ตรง ๆ (*"One `session_scope()` per batch, so the write lock is released between them"*) คนอ่านจึงเชื่อว่ามีคนเฝ้า

**ทางแก้:** เทสใหม่ที่ listen บน `commit` event ของ engine จริง แล้ว assert `timeline[:8] == ["DELETE", "COMMIT"] * 4`

- ไม่ได้เพิ่ม index ไม่ได้เขียน migration (วัดแล้วว่าไม่ต้อง)
- ไม่ได้เพิ่ม setting, env var, endpoint, หน้าเว็บ หรือปุ่มใด ๆ — ใบนี้ไม่มี UI เลยโดยเจตนา
- ไม่ได้เพิ่ม retry, backoff, ตรวจพื้นที่ดิสก์ล่วงหน้า หรือตัวตรวจ backup ที่ไม่สมบูรณ์ · เส้นทางล้มเหลวคือ log, เก็บกวาด temp, ลองใหม่พรุ่งนี้
- ไม่ได้เพิ่ม `ANALYZE`, `VACUUM` ในที่, `PRAGMA optimize` หรือ `wal_checkpoint`
